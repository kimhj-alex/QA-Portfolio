Test Automation

Shoebox
Planner 4 categories · one session · Playwright

Playwright coverage for Shoebox Planner, built in a single session with no prior experience in the tool. Four categories of real, automated tests — and three moments along the way, all inside the geometry category, where an AI's confident first answer turned out to be wrong, caught on instinct before it made it into the suite.

View Test Repository →

"First time using the tool didn't mean first time trusting it without checking."

This was the first Playwright suite built for this portfolio, start to finish, in one afternoon — geometry, UI sync, persistence, and resize-limit coverage, all against the live app. Being new to the tool didn't change the standard: every AI-suggested test, selector, and assumption still got checked against what the app actually did, not what seemed reasonable. Three of those checks turned into their own case studies below, because catching them mattered more than the tool being unfamiliar.

This automation work covers the same app as the Shoebox Planner self-audit and Case Study 01, which covers the app's ellipse math during development.

Four Categories

Each of seven shape variants — square, rotated square, rectangle, rotated rectangle, circle, oval, rotated oval — dragged toward every wall, checking the rendered gap against the room border. This category produced three separate moments worth naming on their own, below the code.

Sample Test — Square vs. Wall

await dragShapeToWall(square, 'top');
expect(await getGapFromWall(square, 'top')).toBeCloseTo(2, 0.3);

await dragShapeToWall(square, 'left');
expect(await getGapFromWall(square, 'left')).toBeCloseTo(2, 0.3);

Moment 01 — Argued Out, Argued Back In

A rotated square was flagged as needing its own test, separate from rotated rectangle. The counter-argument was that both shared the same rotated-corner bounding-box code, so one test covered both. That's true of the code — and beside the point. A user can rotate a square regardless of what the rectangle test already covers, and whether that stays inside the room is a real, separate, user-facing question. The correct call had already been made before the argument started; it just had to be held rather than talked out of.

test('rotated square (40°) clamps to room wall', async ({ page }) => {
  // ...same wall-drag pattern as plain square, at a
  // deliberately non-round rotation angle
});

Moment 02 — The Ellipse Blind Spot, Again

A rotated oval measured as sitting roughly 20px outside the room wall. It wasn't — visually, it stayed inside the whole time. The test was reading getBoundingClientRect(), which measures the shape's invisible rotated rectangular div, not the visible ellipse rendered inside it. That's the same category of mistake Case Study 01 documents in a different AI assistant, months earlier, on the same feature: treating a rotated, asymmetric shape as if rectangle math would cover it. The fix recomputed the true ellipse bounding box, using the app's own formula, applied independently in the test.

const aabbW = 2 * Math.sqrt((rx * cos) ** 2 + (ry * sin) ** 2);
const aabbH = 2 * Math.sqrt((rx * sin) ** 2 + (ry * cos) ** 2);
// measuring the true ellipse, not the rectangular div around it

Moment 03 — Declared Done, Wasn't

Seven shapes were planned. Circle — plain, unrotated, equal width and height — was quietly dropped somewhere in the middle of the session and never written. The category got called complete anyway. It wasn't caught by re-reading the code or re-running anything; it was caught by counting the original list against what actually existed, and saying so directly rather than letting a confident "done" stand unchecked.

Clicking furniture should highlight its sidebar entry, and clicking a sidebar entry should highlight the furniture — in both directions, on both desktop and iPad. Two of the four directions are already-documented findings from the self-audit; this automates all four, bugs included, rather than only the parts that pass.

Sample Test — RP-002, Documenting the Known Bug

await sidebarEntry.click();
// RP-002: furniture should NOT get "selected" — documents the known bug
await expect(shape).not.toHaveClass(/selected/);

Result

Canvas → list highlight confirmed working on both platforms. List → canvas highlight confirmed broken on desktop (RP-002) and confirmed working on iPad. Color-swatch tap confirmed broken on iPad (RP-007) and confirmed working on desktop.

A full save → saved-rooms list → reopen flow, automated end to end, confirming a finding the self-audit already documented: layer order reverses on reload. Scoped to that one numbered finding rather than padded with unrelated checks that don't carry an RP number.

Sample Test — RP-004

// RP-004: order should be reversed, not preserved
expect(namesAfter).toEqual([...namesBefore].reverse());

Font size has an enforced min and max in the code. Furniture width and height do not — this category set out to find out what that actually means in practice, since nobody had tested it before.

Sample Test — Two Ways to Enter the Same Value

// Typing "-20" directly: field shows it, rendered width barely changes
// Decrementing via the spinner into negative: rendered width hits 0
expect(finalValue).toBeLessThan(0);
expect(renderedWidth).toBe(0);

Result

Zero or negative width makes furniture invisible but fully interactive — still clickable and draggable at its exact former position. No upper bound exists on the raw dimension, but the wall-clamping logic from Category 01 still contains it. Typing a negative value directly is silently ignored by the app; reaching the same value through the spinner actually applies it — two different real behaviors from the same typed number.

Methodology

"Each case started the same way — an AI gave a confident answer, and it didn't hold up once checked."

Building this test suite meant working with AI at every step — deciding what to test, writing the Playwright code, reading what the results actually meant. The three moments inside the geometry category are what came out of paying attention to that process, not just its output. None of them required deep technical knowledge to catch: a rotated shape either needs its own test or it doesn't, a shape either stays inside the room or it doesn't, a planned shape either got tested or it didn't. What mattered was checking the AI's answer against the plain version of the question, instead of accepting a more technical-sounding one in its place.
