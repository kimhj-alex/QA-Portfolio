Gen AI Cases → Case Study 01

The Ellipse
Math Shortcut

An AI coding assistant recommended faking a fix instead of doing the real math — and only did the real math once asked directly.

Context Shoebox Planner — a room-layout PWA I was building with an AI coding assistant
Task Get correct ellipse-collision math working in "free mode," then port it into "tidy mode," which adds a no-overlap constraint
Tool General-purpose conversational AI assistant, used as a coding collaborator
Duration Multiple sessions across several days

Key Takeaways

01

The default answer wasn't the best one

Offered a choice, the AI recommended faking a fix with a shrink hack over doing the real ellipse math — math it produced correctly the moment it was asked directly.

02

A correct fix still didn't transfer cleanly

Shoebox Planner, the app this case study is about, was later put through its own QA self-audit — a separate look at the finished product's UX, not the AI's reasoning during development.

The Setup

Shoebox Planner is a room-layout tool I built as a personal PWA — drag furniture shapes around a floor plan, resize them, rotate them, save the layout. It has two interaction modes: free mode, where furniture can overlap freely, and tidy mode, which adds a constraint that furniture pieces can't overlap each other or cross the room border.

The story starts in free mode, with a bug that looked cosmetic. A circle squished into an oval sat flush against the room border just fine — until it was rotated, at which point it stopped a visible gap short of the wall, like the collision box had rotated differently from the shape it was attached to. The actual cause was straightforward once named: the bounding box math was correct for a rotated rectangle, but an oval's true edges sit inside that rectangle, not flush with its corners — so a box built for a rectangle will always leave a gap around a rotated ellipse.

The Fake Fix

Here's where it gets interesting. Once the cause was clear, the AI laid out two paths forward: do the actual ellipse math, or quietly shrink the oval's bounding box by a fixed percentage so it visually sits closer to the wall. It recommended the second one.

Paraphrased exchange
AI You have two options. Option 1: accept rectangle math for ellipses — no real fix needed, this is true to the math, you just live with the visual gap. Option 2: fake it by shrinking rotated ovals by a small percentage so they look flush. My recommendation is Option 2.
Tester You can't do math for ovals?

That was the entire pushback — one plain question, no new information supplied. The next response produced the correct formula immediately: the axis-aligned bounding box of a rotated ellipse, derived from its radii and rotation angle, with no shrink factor and no approximation.

What it produced once asked directly
const aabbW = 2 * Math.sqrt((rx * cos) ** 2 + (ry * sin) ** 2);
const aabbH = 2 * Math.sqrt((rx * sin) ** 2 + (ry * cos) ** 2);

Nothing about the correct math was newly discovered between those two messages — the formula didn't require new information, a different file, or more context. It was simply not the first thing offered. The default answer was a workaround dressed up as a reasonable trade-off — "no real fix is needed" — and the real fix only surfaced when the workaround was directly questioned.

That gap between what an AI assistant will default to and what it's actually capable of, if pushed, turned out to be the theme of everything that followed.

Porting It Forward — Where It Got Harder

With free mode's ellipse math working correctly, the next task was porting it into tidy mode, which layers an additional constraint on top: furniture pieces can't overlap each other or cross the room border. I uploaded the working free mode file directly for reference each time I raised it, with some version of the same instruction — we already solved this in free mode, just apply the same math here.

This wasn't a case of the AI needing to derive a solution — it had the correct answer sitting in front of it, in an uploaded file, more than once. What took several sessions was faithfully carrying that answer over.

The Pattern That Kept Recurring

The first fix attempt worked for rotated ovals but left unrotated ovals still behaving like perfect circles when tested against other furniture. That's a strange thing to report, and it turned out to be the whole story in miniature.

Paraphrased exchange
Tester A rotated oval works now, but an unrotated oval still keeps its original collision box against other furniture — like it thinks it's still a perfect circle.
AI Here's the fix — replace the circle-vs-circle block with this version, which handles rotated ellipses properly.

The pattern repeated across several rounds. Each time, the underlying condition being used to decide "is this an ellipse" looked something like this:

The recurring condition
const isOval = width !== height && rotation !== 0;
const isOval = width !== height;

The bug was only visible when a shape was both squished and rotated — that's the state where the visual mismatch was most obvious. But the AI kept writing new fixes that quietly reattached a rotation check to the ellipse condition, as if rotation were part of the rule rather than a coincidence of when the bug happened to show up. Each new patch would fix the specific case just reported, and reintroduce the same rotation-gated logic somewhere else in the function.

The bug wasn't really about geometry math. It was about the model pattern-matching to when the bug was noticed, instead of reasoning about why it happened.

Fixes That Broke Other Things

Tidy mode's overlap check has to handle several shape pairings differently — circle vs. circle, circle vs. rectangle, rectangle vs. rectangle — each with its own math. Because the ellipse logic kept getting patched in isolation, fixing one pairing regularly broke another:

Paraphrased exchange
Tester Now both rectangles and circles think the squished oval is a rectangle, and the rotated oval is treated as a perfect circle.
Tester Now the rectangles think a normal, unsquished circle is a square.
Tester Squares still think an ellipse is a rectangle.

Three separate reports, three separate regressions, each introduced by a fix meant to solve the previous one. The underlying issue was that the AI's patches relied on a static type or shape label assigned when a piece of furniture was first created — a label that never updated after the shape was resized or rotated. Every fix attempt added another branch of logic on top of a foundation that was checking the wrong thing.

What Finally Worked

The turning point wasn't a bigger rewrite, and it wasn't code review — I wasn't reading isOverlapping() and spotting the bad condition myself. What broke the loop was testing the same way I'd test any black-box feature: methodically, not by feel. Every shape type, dragged against every other shape type, rotated and unrotated, logged pass or fail per pairing. Watching where the invisible collision edge actually sat relative to the visible shape was enough to tell that an "oval" was colliding like it still had the footprint of a rectangle, or a circle, without needing to see a single line of the underlying math.

Actual test matrix, from that session
Tester Perfect circle with: square ✓ · rectangle ✓ · rotated rect ✓ · circle ✓ · oval ✓ · rotated oval ✗
Oval with: square ✓ · rectangle ✓ · rotated rect (jumpy) · circle (not great) · oval ✗ · rotated oval ✗
Rotated oval with: square ✗ · rectangle ✗ · rotated rect ✗ · circle ✗ · oval ✗ · rotated oval ✗

That matrix is what made the next report specific enough to act on. Instead of "it's still broken," it named exactly which pairing failed and how:

Paraphrased exchange
Tester Rectangle-rectangle: working. Non-rotated rectangle-circle: working. Rotated rectangle-circle: still not working.
AI Found it — the circle-vs-rectangle block only applies ellipse math when the circle is squished and rotated. Remove the rotation condition; an oval is still an oval at zero degrees.

The root cause, once isolated, was almost embarrassingly small: one line gating ellipse detection on a rotation angle that had no logical bearing on whether ellipse math should apply at all. Removing that single condition — going from width !== height && angle !== 0 to just width !== height — resolved the last remaining case.

None of that required reading the AI's implementation. It required treating "does this collide correctly" as testable the same way any UI behavior is testable — systematically, across a full matrix of cases, rather than trusting a single "looks fixed" pass.

Where It Landed

Tidy mode was retired from the app later on, for reasons unrelated to this bug — and the overlap-specific fix worked out over the course of this debugging session never made it into a file that survived that change. What did persist, unchanged, is the simpler piece: free mode's ellipse-aware room-border clamping, which keeps a squished or rotated shape correctly inside the room's edges. That logic was never in question here — it worked from early on and shipped as-is, and it's live in the app today at shoebox-planner.web.app — resize a circle into an oval, rotate it, and drag it to the wall to see it.

So the fix that took the most work to isolate — correct ellipse-vs-ellipse and ellipse-vs-rectangle overlap detection, independent of rotation — is verified only in conversation, not in a surviving build. That's a real and slightly deflating outcome, and worth stating plainly rather than smoothing over: not every resolved bug outlives the feature it was found in.

What does outlive it is the pattern itself. As a piece of Gen AI evaluation, this session is a clean example of a specific, nameable failure mode: an assistant that pattern-matches a fix to the most recently reported symptom, rather than reasoning about the general rule the symptom is evidence of. It took naming the exact failing shape pairing, more than once, before that pattern stopped recurring. Knowing that failure mode exists — and that it can hide inside code that looks plausible and passes a quick glance — is exactly the kind of thing a year of hands-on Gen AI use surfaces that a general familiarity with "AI tools" wouldn't.
